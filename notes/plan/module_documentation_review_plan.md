## 一、审查方法论

### 1.1 审查流程

对每个模块,按以下步骤进行审查:

```
1. 代码探索阶段
   ├── 使用 Explore agent 深度探索模块代码
   ├── 分析所有 keeper/ 文件
   ├── 分析所有 types/ 数据结构
   ├── 分析所有测试文件 (*_test.go)
   ├── 识别所有消息类型 (Msg*)
   ├── 识别所有 ABCI 钩子
   └── 识别所有存储键和数据结构

2. 文档对比阶段
   ├── 读取现有 PRD 文档
   ├── 读取现有数据结构文档
   ├── 读取现有架构文档
   ├── 对比代码探索结果与文档
   └── 列出遗漏内容清单

3. 分级与优先级排序
   ├── P0 (高优先级): 核心功能、关键业务规则
   ├── P1 (中优先级): 辅助功能、配置参数
   └── P2 (低优先级): 边缘功能、已废弃特性

4. 文档完善阶段
   ├── 按优先级补充 PRD 文档
   ├── 按优先级补充数据结构文档
   └── 按优先级补充架构文档

5. 验证与 Review 阶段
   ├── 验证公式和参数准确性
   ├── 验证用户场景完整性
   ├── 验证文档间一致性
   └── 与代码探索报告交叉验证
```

## 四、文档完善规范

### 4.1 PRD 文档补充规范

#### 必须包含的元素

1. **功能需求 (FR-X)**
   - 需求描述: 清晰的产品功能说明
   - 功能点: 具体的功能列表
   - 业务规则: 产品行为规则 (非技术实现)
   - 验收标准: 可测试的验收条件
   - 用户场景: 完整的用户操作流程

2. **公式文档化** (如果涉及计算)
   - 数学表达式: 使用标准数学符号
   - 变量说明: 每个变量的定义和单位
   - 计算示例: 带入实际数值演示
   - 业务解释: 用通俗语言解释公式含义

3. **非功能需求 (NFR-X)**
   - 性能要求: 响应时间、吞吐量
   - 可靠性要求: 可用性、确定性
   - 安全性要求: 风险控制、攻击防护
   - 系统限制: 硬编码常量、配置参数

#### 禁止的内容
- ❌ 代码片段 (除非作为配置示例)
- ❌ 技术术语 (如 Keeper, KVStore, TransientStore)
- ❌ 实现细节 (如算法复杂度、数据结构)

### 4.2 数据结构文档补充规范

#### 必须包含的元素

1. **存储键定义**
   - 键前缀: 精确的前缀字符串
   - 键组成: 完整的键构造方式
   - 示例: 实际的键示例

2. **数据结构定义**
   - Go 结构体定义 (简化版)
   - 字段说明: 每个字段的业务含义
   - 枚举值: 所有可能的枚举值和含义

3. **业务含义说明**
   - 该数据结构的作用
   - 为什么需要这个数据结构
   - 数据的生命周期

4. **使用场景**
   - 何时写入
   - 何时读取
   - 何时删除

5. **数据访问示例**
   - Keeper 方法调用示例
   - 读/写/删除示例

6. **关键文件引用**
   - 数据结构定义文件 (带行号)
   - Keeper 实现文件

#### 分类组织

按存储类型分类:
- **StateStore**: 链上持久化存储
- **MemStore**: 内存缓存
- **TransientStore**: 区块级瞬态存储
- **纯内存**: 不持久化的数据结构

### 4.3 架构文档补充规范

#### 必须包含的元素

1. **组件职责说明**
   - 各组件的作用
   - 组件间的协作关系
   - 组件边界

2. **ABCI 生命周期集成**
   - PreBlocker: 初始化逻辑
   - BeginBlocker: 区块开始逻辑
   - EndBlocker: 区块结束逻辑
   - PrepareCheckState: CheckTx 准备逻辑
   - Precommit: 副作用处理

3. **核心业务流程**
   - 流程图或序列图 (ASCII 或 Mermaid)
   - 关键步骤说明
   - 数据流向

4. **技术决策记录 (ADR)**
   - 问题: 为什么需要这个设计?
   - 方案: 选择的方案
   - 权衡分析: 优缺点对比
   - 影响: 对系统的影响

#### 重点强调
- ✅ 描述**为什么**这样设计 (而非**是什么**)
- ✅ 技术决策要有权衡分析
- ✅ 数据流和组件交互要清晰
- ✅ 不包含代码细节,专注架构层面

## 六、风险与注意事项

### 6.1 文档膨胀风险
- **风险**: 补充大量内容可能导致文档过长,不易阅读
- **缓解**:
  - 保持简洁,聚焦核心内容
  - 使用表格和公式简化说明
  - 使用章节折叠 (如果支持)
  - 将过于详细的内容移到附录

### 6.2 代码演进风险
- **风险**: 代码可能在未来版本中变化,导致文档过时
- **缓解**:
  - 在文档中标注"基于代码版本: commit XXX"
  - 定期审查和更新文档 (建议每个版本发布前)
  - 在代码注释中标注对应的文档位置

### 6.3 理解偏差风险
- **风险**: 基于代码探索的理解可能与实际设计意图有偏差
- **缓解**:
  - 标注不确定的内容,提示"需进一步验证"
  - 与团队成员 review 确认
  - 对照测试用例验证理解

### 6.4 模块间一致性风险
- **风险**: 不同模块文档间可能出现术语或描述不一致
- **缓解**:
  - 建立统一的术语表 (Glossary)
  - 在完成所有模块后进行交叉验证
  - 使用搜索工具检查术语一致性
