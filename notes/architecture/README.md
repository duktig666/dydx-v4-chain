# Hermes DEX 架构文档总览

## 📖 文档简介

本目录包含 Hermes DEX 交易系统 7 个核心模块的架构设计文档。这些文档从系统架构师的视角,详细描述了每个模块的设计理念、技术决策、模块间协作和权衡分析。

**文档特点**:
- ✅ **强调"为什么"而非"是什么"**: 重点阐述设计理由和权衡分析
- ✅ **包含技术决策记录 (ADR)**: 记录关键技术选择的背景和理由
- ✅ **详细的数据流和组件交互**: 可视化展示模块内部和模块间协作
- ✅ **公式文档化**: 对核心计算公式进行详细解释和示例演示

## 🏗️ 系统整体架构

### 分层架构

Hermes DEX 采用**分层架构**,模块按职责分为三层:

```
┌─────────────────────────────────────────────────┐
│               应用层 (Application Layer)         │
│  ├─ Listing (市场创建)                          │
│  └─ Vault (自动做市)                            │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│               核心层 (Core Layer)                │
│  ├─ CLOB (订单匹配引擎)                         │
│  ├─ Subaccounts (账户与保证金)                  │
│  └─ Stats (交易统计)                            │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│               基础层 (Foundation Layer)          │
│  ├─ Perpetuals (合约配置)                       │
│  ├─ Prices (价格预言机)                         │
│  └─ Leverage (杠杆管理 - 集成)                  │
└─────────────────────────────────────────────────┘
```

### 核心数据流

```
        订单放置 → 匹配 → 成交完整数据流

用户
  │ 提交订单
  ▼
CLOB 模块
  ├──> Subaccounts (验证保证金)
  ├──> Perpetuals (获取合约配置)
  ├──> Prices (获取预言机价格)
  │
  │ 订单进入 MemClob
  ▼
匹配引擎
  │ 价格-时间优先匹配
  ▼
成交处理
  ├──> Subaccounts (更新余额和持仓)
  ├──> Perpetuals (更新未平仓合约量)
  └──> Stats (记录成交统计)
```

## 📊 模块功能总览

### 1. CLOB 模块 - 核心交易引擎

**职责**: 订单簿管理、订单匹配、清算执行

**关键设计**:
- **MemClob**: 纯内存订单簿,性能优先
- **短期/长期订单分离**: 优化存储和匹配效率
- **MEV 保护**: 速率限制、权益层级限制、确定性匹配

**核心流程**:
- 订单放置 → 保证金验证 → 进入订单簿 → 匹配引擎 → 成交结算
- 清算触发 → 账户筛选 → 清算订单生成 → 强制平仓

**技术决策**:
- 为什么使用 MemClob? → 性能是核心要求 (内存访问比磁盘快 1000 倍)
- 为什么区分短期/长期订单? → 存储优化 (短期订单自动过期)
- 为什么在 DeliverTx 匹配? → 确保共识一致性

**详细文档**: [clob.md](./clob.md)

---

### 2. Perpetuals 模块 - 永续合约配置

**职责**: 永续合约定义、资金费率计算、流动性层级管理

**关键设计**:
- **两层周期机制**: 1 分钟溢价采样 + 1 小时资金费率结算
- **OIMF**: 基于未平仓合约量动态调整保证金
- **聚合算法**: 溢价用中位数,资金费率用平均值

**核心流程**:
- 溢价采样 (1 分钟) → 聚合为样本 → 计算资金费率 (1 小时) → 结算到持仓

**核心公式**:

**OIMF 计算**:
```
if OI <= LowerCap: OIMF = 0%
elif LowerCap < OI < UpperCap: OIMF = (OI - LowerCap) / (UpperCap - LowerCap) * 100%
else: OIMF = 100%

AdjustedIMR = BaseIMR + OIMF * (BaseIMR - MaintenanceMarginRate)
```

**资金费率计算**:
```
FundingRate = Clamp(8 * AvgPremium, DefaultFundingPpm - MaxPremiumPpm, DefaultFundingPpm + MaxPremiumPpm)
```

**技术决策**:
- 为什么两层周期? → 平衡响应速度和稳定性
- 为什么溢价用中位数? → 抗操纵,避免异常值
- 为什么需要 OIMF? → 防止大额持仓操纵市场

**详细文档**: [perpetuals.md](./perpetuals.md)

### 3. Listing 模块 - 市场上市管理

**职责**: 无需许可的市场创建、默认参数配置

**关键设计**:
- **一键市场创建**: 单条消息创建 Perpetual + Market + CLOBPair
- **默认参数自动配置**: 根据市值选择流动性层级
- **Vault 存款门槛**: 防止垃圾市场

**核心流程**:
- 验证硬上限 → 存入 Vault 存款 → 创建 Perpetual → 创建 Market → 创建 CLOBPair → 激活交易

**技术决策**:
- 为什么一键创建? → 降低市场创建门槛,提高用户体验
- 为什么需要 Vault 存款? → 防止垃圾市场,确保初始流动性
- 为什么使用默认参数? → 简化流程,降低配置复杂度

**详细文档**: [listing.md](./listing.md)

---

### 4. Prices 模块 - 价格预言机集成

**职责**: Slinky Oracle 集成、价格验证、价格存储

**关键设计**:
- **Slinky Oracle**: 通过 Vote Extensions 提交价格
- **价格验证**: Towards/Crossing 条件防止异常价格
- **快速更新**: 每个区块更新价格

**核心流程**:
- 验证器提交价格 (Vote Extensions) → 聚合价格 → 验证 Towards/Crossing → 存储到 StateStore

**核心公式**:

**Towards 条件** (价格向指数价格靠拢):
```
|newPrice - indexPrice| <= |oldPrice - indexPrice|
```

**Crossing 条件** (价格跨越指数价格):
```
newDelta² × 1,000,000 <= oldDelta × tickSizePpm
即: newDelta <= sqrt(oldDelta × tickSize)
```

**技术决策**:
- 为什么使用 Slinky Oracle? → 去中心化,抗审查
- 为什么使用 Vote Extensions? → 性能优化,无需额外交易
- 为什么需要价格验证? → 防止异常价格导致错误清算

**详细文档**: [prices.md](./prices.md)

---

### 5. Stats 模块 - 交易统计

**职责**: 用户交易统计、手续费分级、联盟费用追踪

**关键设计**:
- **30 天滚动窗口**: 自动清理过期数据,防止状态膨胀
- **Taker/Maker 分离**: 支持差异化手续费
- **Epoch 级别聚合**: 减少存储,便于查询

**核心流程**:
- 成交记录 → 累积到 BlockStats (TransientStore) → EndBlocker 聚合到 EpochStats → 定期清理 30 天前数据

**技术决策**:
- 为什么使用 30 天窗口? → 平衡存储成本和手续费分级需求
- 为什么区分 Taker/Maker? → 支持差异化手续费率
- 为什么 Epoch 级别聚合? → 减少存储,便于按周期查询

**详细文档**: [stats.md](./stats.md)

### 6. Vault 模块 - 自动化做市

**职责**: Megavault 管理、份额机制、自动订单刷新

**关键设计**:
- **份额机制**: 公平分配盈亏,自动计算价值
- **提款解锁期**: 防止闪电贷攻击
- **自动做市**: EndBlocker 每个区块刷新订单

**核心流程**:
- 存款: 转账 USDC → 计算份额 → 铸造份额
- 提款: 锁定份额 → 解锁期 → 转账 USDC → 销毁份额
- 订单刷新: 取消旧订单 → 获取价格 → 计算报价 → 放置新订单

**核心公式**:

**份额价值计算**:
```
ShareValue = VaultEquity / TotalShares
```

**订单报价计算**:
```
BidPrice = OraclePrice × (1 - Spread / 2)
AskPrice = OraclePrice × (1 + Spread / 2)
OrderSize = VaultEquity × PositionSizePct / OraclePrice
```

**技术决策**:
- 为什么使用份额机制? → 公平分配盈亏,无需复杂会计
- 为什么需要解锁期? → 防止闪电贷攻击
- 为什么每个区块刷新订单? → 确保流动性始终可用

**详细文档**: [vault.md](./vault.md)

---

### 7. Leverage 模块 - 杠杆管理 (集成模块)

**职责**: 杠杆倍数设置、保证金计算集成

**关键设计**:
- **集成设计**: 无独立 Keeper,数据在 CLOB,逻辑在 Subaccounts
- **保证金验证**: 杠杆调整时验证保证金充足性
- **行业标准**: 使用杠杆倍数 (20x) 而非保证金率 (5%)

**核心流程**:
- 用户更新杠杆 → CLOB 验证 → Subaccounts 验证保证金 → 更新 StateStore

**核心公式**:

**保证金要求计算**:
```
IMR = 1 / Leverage
MarginRequirement = PositionValue × IMR
```

**技术决策**:
- 为什么没有独立 Keeper? → 功能简单,集成设计更高效
- 为什么数据存储在 CLOB? → CLOB 频繁读取,本地存储性能高
- 为什么使用杠杆倍数? → 符合行业惯例,用户体验好

**详细文档**: [leverage.md](./leverage.md)

## 📐 关键技术决策总结

### 性能优化决策

| 决策                  | 模块        | 理由                          | 权衡                          |
|---------------------|-----------|------------------------------|------------------------------|
| MemClob 纯内存订单簿  | CLOB      | 性能优先 (内存快 1000 倍)      | 内存消耗高,需要每区块重建      |
| 短期订单自动过期      | CLOB      | 减少存储,自动清理              | 长期订单需要额外存储           |
| 杠杆数据在 CLOB      | Leverage  | 本地读取,减少跨模块调用        | 逻辑耦合                      |

### 安全性决策

| 决策                  | 模块        | 理由                          | 权衡                          |
|---------------------|-----------|------------------------------|------------------------------|
| 提款解锁期            | Vault     | 防止闪电贷攻击                 | 用户体验稍差,资金锁定          |
| 价格验证 (Towards/Crossing) | Prices | 防止异常价格导致错误清算       | 可能拒绝合理价格               |
| 保证金验证            | Leverage  | 防止用户绕过风控               | 可能拒绝杠杆调整               |

### 存储优化决策

| 决策                  | 模块        | 理由                          | 权衡                          |
|---------------------|-----------|------------------------------|------------------------------|
| 30 天滚动窗口         | Stats     | 防止状态膨胀                   | 历史数据丢失                   |
| Epoch 级别聚合        | Stats     | 减少存储,便于查询              | 细粒度数据丢失                 |
| TransientStore 区块聚合 | Stats   | 减少 StateStore 写入次数       | 增加存储层次                   |
