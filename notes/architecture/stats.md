# Stats 模块架构设计

## 1. 模块概述

### 1.1 职责定义

Stats (统计) 模块负责 Hermes DEX 的**交易统计和手续费分级**,职责包括:

- **用户交易统计**: 追踪用户 30 天交易量
- **手续费分级**: 根据交易量计算手续费折扣
- **联盟费用支持**: 追踪推荐者和被推荐者的成交量
- **全局统计**: 追踪系统总交易量

### 1.2 核心功能

**30 天滚动窗口机制**:
- 自动清理 30 天前的数据
- 实时计算用户累计交易量
- Epoch 级别数据聚合

**Taker/Maker 成交量分离**:
- 区分主动成交 (Taker) 和被动成交 (Maker)
- 支持差异化手续费率

**联盟费用计算**:
- 追踪推荐者产生的成交量
- 追踪被推荐者的成交量
- 支持推荐奖励分配

### 1.3 关键约束

**存储效率**:
- 30 天窗口,自动清理旧数据
- 防止状态膨胀

**确定性要求**:
- 统计更新必须确定性
- 排序保证稳定

## 2. 架构设计

### 2.1 组件结构

```
Stats 模块架构

┌─────────────────────────────────────────────────┐
│         gRPC Query Server (查询接口)             │
│  UserStats, GlobalStats, EpochStats             │
└─────────────────────────────────────────────────┘
                       ↕
┌─────────────────────────────────────────────────┐
│         Msg Server (消息处理器)                  │
│  UpdateParams (更新窗口时长)                    │
└─────────────────────────────────────────────────┘
                       ↕
┌─────────────────────────────────────────────────┐
│              Keeper Layer (业务逻辑层)           │
│  ├─ RecordFill() (记录成交)                     │
│  ├─ ProcessBlockStats() (聚合区块统计)          │
│  ├─ ExpireOldStats() (清理过期数据)             │
│  └─ Query Functions (查询统计)                  │
└─────────────────────────────────────────────────┘
                       ↕
┌─────────────────────────────────────────────────┐
│              Storage Layer (存储层)              │
│  ├─ StateStore (用户统计、Epoch 统计、全局统计) │
│  └─ TransientStore (区块统计)                   │
└─────────────────────────────────────────────────┘
```

### 2.2 存储架构

#### StateStore (链上持久化存储)

**存储内容** (4 个数据结构):

1. **UserStats** (用户统计):
   - TakerNotional: Taker 累计成交额 (30天)
   - MakerNotional: Maker 累计成交额 (30天)
   - Affiliate_30DRevenueGeneratedQuantums: 联盟费用收入
   - Affiliate_30DReferredVolumeQuoteQuantums: 推荐成交量
   - Affiliate_30DAttributedVolumeQuoteQuantums: 被推荐成交量

2. **EpochStats** (Epoch 统计):
   - EpochEndTime: Epoch 结束时间
   - Stats: []UserEpochStats (该 Epoch 的用户统计列表)

3. **GlobalStats** (全局统计):
   - NotionalTraded: 30 日滚动窗口总成交量

4. **StatsMetadata** (统计元数据):
   - TrailingEpoch: 滑动窗口尾部 Epoch
   - LatestEpochNumber: 最新 Epoch 编号

#### TransientStore (区块级瞬态存储)

**存储内容** (1 个数据结构):

**BlockStats** (区块统计):
- Fills: []Fill (当前区块所有成交记录)
- 每个 Fill 包含: Taker, Maker, Notional, AffiliateFee, Attributions

**为什么使用 TransientStore?**

**区块级聚合**:
- 当前区块的成交记录暂存
- EndBlocker 统一聚合到 EpochStats
- 减少 StateStore 写入次数

## 3. 核心业务流程

### 3.1 统计更新流程

```
        订单成交 → 统计更新完整流程

┌─────────────────────────────────────────────────┐
│    CLOB: 订单成交                                │
│    Fill {                                       │
│      TakerOrder, MakerOrder,                    │
│      Notional, AffiliateFee,                    │
│      AffiliateAttributions                      │
│    }                                            │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│    CLOB 调用 Stats.RecordFill(fill)             │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│    RecordFill()                                 │
│    ├─ 提取 Taker/Maker 地址                     │
│    ├─ 计算成交名义本金                          │
│    ├─ 提取联盟费用数据                          │
│    └─ 附加到 TransientStore.BlockStats          │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│    EndBlocker: ProcessBlockStats()              │
│    ├─ 获取当前 Epoch 信息                       │
│    ├─ 检索该 Epoch 的 EpochStats                │
│    ├─ 遍历 BlockStats 中的每个 Fill             │
│    │   ├─ 更新 Taker 的 EpochStats               │
│    │   │   TakerNotional += Fill.Notional       │
│    │   ├─ 更新 Maker 的 EpochStats               │
│    │   │   MakerNotional += Fill.Notional       │
│    │   └─ 处理联盟费用归属                      │
│    ├─ 按用户地址排序 (确定性)                   │
│    ├─ 持久化到 StateStore.EpochStats            │
│    ├─ 更新 UserStats (累计 30 天)               │
│    └─ 更新 GlobalStats                          │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
            统计更新完成
```

### 3.2 过期统计清理流程 (30天滚动窗口)

```
        ExpireOldStats() 清理流程

┌─────────────────────────────────────────────────┐
│    EndBlocker: 每个区块检查                      │
│    是否有 Epoch 超出 30 天窗口?                  │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│    获取当前 Epoch 和 TrailingEpoch               │
│    ├─ CurrentEpoch = GetCurrentEpoch()          │
│    └─ TrailingEpoch = GetTrailingEpoch()        │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│    检查 TrailingEpoch 是否过期                   │
│    if EpochEndTime + WindowDuration < Now:      │
│       → 过期,需要删除                           │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│    删除过期 EpochStats                           │
│    ├─ removedStats = GetEpochStats(TrailingEpoch) │
│    └─ DeleteEpochStats(TrailingEpoch)           │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│    从 GlobalStats 递减                           │
│    GlobalStats.NotionalTraded -= removedStats.TakerNotional │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│    从 UserStats 递减                             │
│    for user in removedStats.Stats:              │
│      UserStats[user].TakerNotional -= ...       │
│      UserStats[user].MakerNotional -= ...       │
│      (处理 uint64 下溢保护)                     │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│    更新 TrailingEpoch 指针                       │
│    TrailingEpoch += 1                           │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
            清理完成
        (30 天窗口保持滚动)
```

#### 为什么使用 30 天滚动窗口?

**问题**: 统计数据应该保留多久?

**备选方案**:

1. **方案 A: 永久保留**
   - ❌ 状态膨胀
   - ❌ 存储成本高

2. **方案 B: 滚动窗口** ✅ 最终选择
   - ✅ 自动清理,防止膨胀
   - ✅ 足够时间计算手续费分级
   - ❌ 历史数据丢失

**30 天选择理由**:
- 符合手续费分级周期
- 平衡存储成本和数据需求
- 业界标准做法

**决策理由**: 平衡存储成本和业务需求

## 4. 技术决策记录 (ADR)

### 4.1 为什么区分 Taker 和 Maker?

**问题**: 是否需要区分主动成交和被动成交?

**原因分析**:

**手续费差异化**:
- Taker (主动成交): 消耗流动性,手续费较高
- Maker (被动成交): 提供流动性,手续费较低或负费率

**交易行为分析**:
- 高频做市商: Maker 成交量大
- 普通交易者: Taker 成交量大
- 区分有助于分析用户行为

**决策理由**: 支持差异化手续费和用户分析

### 4.2 为什么使用 Epoch 级别聚合?

**问题**: 统计数据应该如何组织?

**备选方案**:

1. **方案 A: 区块级别**
   - ❌ 数据量大
   - ❌ 查询复杂

2. **方案 B: Epoch 级别** ✅ 最终选择
   - ✅ 数据聚合,减少存储
   - ✅ 便于按周期查询
   - ✅ 便于清理过期数据

**决策理由**: 平衡存储效率和查询需求

## 5. 总结

### 5.1 关键设计亮点

1. **30 天滚动窗口**: 自动清理,防止状态膨胀
2. **Taker/Maker 分离**: 支持差异化手续费
3. **Epoch 级别聚合**: 平衡存储和查询
4. **联盟费用支持**: 推荐奖励机制

### 5.2 设计权衡

| 设计选择              | 优势                 | 劣势                 | 决策理由             |
|---------------------|---------------------|---------------------|---------------------|
| 滚动窗口             | 防止状态膨胀         | 历史数据丢失         | 存储效率优先         |
| Epoch 聚合          | 减少存储             | 细粒度数据丢失       | 平衡存储和查询       |
| TransientStore      | 区块级聚合           | 增加存储层次         | 性能优化             |
