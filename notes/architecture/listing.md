# Listing 模块架构设计

## 1. 模块概述

### 1.1 职责定义

Listing (市场上市) 模块负责 Hermes DEX 的**无权限市场创建**,职责包括:

- **无权限上市**: 允许任何人创建新的永续合约市场
- **市场硬上限管理**: 限制可创建的市场总数,防止滥用
- **Vault 存款协调**: 为新市场自动配置 Megavault 流动性
- **隔离到交叉升级**: 管理永续合约保证金模式转换

### 1.2 核心功能

**CreateMarketPermissionless** (无权限上市):
- 一键创建: 价格市场 + 永续合约 + CLOB 交易对 + Vault 流动性
- 自动配置: 默认参数,无需手动配置
- Vault 激活: 自动为新市场提供做市流动性

**市场硬上限**:
- 防止市场数量爆炸
- 可通过治理调整

**保证金模式升级**:
- Isolated → Cross 转换
- 保险基金和抵押品转移

### 1.3 关键约束

**安全性要求**:
- 防止恶意创建大量市场
- 验证市场参数有效性
- 确保 Vault 存款充足

**权限控制**:
- 市场创建: 无权限 (任何人)
- 硬上限调整: 需要治理
- 保证金模式升级: 需要 Authority

### 2.2 存储架构

#### StateStore (链上持久化存储)

**存储内容** (2 个数据结构):

1. **HardCapForMarkets** (市场硬上限):
   - 类型: uint32
   - 默认值: 500
   - 用途: 限制可创建的市场总数

2. **ListingVaultDepositParams** (Vault 存款参数):
   - NewVaultDepositAmount: 新 Vault 存款金额 (默认 10,000 USDC)
   - MainVaultDepositAmount: 主 Vault 存款金额 (默认 0 USDC)
   - NumBlocksToLockShares: 锁定期 (默认 2,592,000 区块 ≈ 30天)

**为什么 Listing 模块存储极少?**

**原因分析**:

**Listing 是协调者,不是存储者**:
- 市场数据存储在 Prices 模块
- 永续合约存储在 Perpetuals 模块
- 交易对存储在 CLOB 模块
- Vault 数据存储在 Vault 模块

**Listing 只存储配置**:
- 硬上限: 限制市场数量
- Vault 参数: 默认存款配置

**设计权衡**:
- ✅ 优势: 轻量级,职责单一
- ❌ 劣势: 依赖多个模块
- 决策理由: 关注点分离,模块化设计

### 2.3 ABCI 生命周期集成

**Listing 模块无 ABCI 钩子**:
- 无 PreBlocker
- 无 BeginBlocker
- 无 EndBlocker

**原因**: Listing 是按需操作,不需要周期性任务

## 3. 核心业务流程

### 3.1 无权限市场创建流程

```
        CreateMarketPermissionless 完整流程

┌─────────────────────────────────────────────────┐
│    用户提交 MsgCreateMarketPermissionless       │
│    ├─ Ticker: "BTC-USD"                         │
│    └─ (其他参数从 MarketMap 自动获取)           │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│    第1步: 验证硬上限                            │
│    ├─ 获取当前市场数量                          │
│    ├─ 检查是否 < HardCapForMarkets              │
│    └─ 超过限制 → 拒绝                           │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼

│    第2步: 从 MarketMap 获取市场元数据           │

                    │

│    第5步: 创建 CLOB 交易对 (CLOB 模块)          │
│    ClobKeeper.CreateClobPair()                  │

│    ├─ StepBaseQuantums = 1,000,000              │
│    ├─ SubticksPerTick = 1,000,000               │
│    ├─ QuantumConversionExponent = -9            │
│    └─ Status = ACTIVE                           │
└───────────────────┬─────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│    第6步: Vault 存款流程 (Vault 模块)           │
│    ├─ 计算总存款                                │
│    │   = NewVaultDepositAmount                  │
│    │   + MainVaultDepositAmount                 │
│    │                                             │
│    ├─ 向 Megavault 存款                         │
│    │   VaultKeeper.DepositToMegavault()         │
│    │   → 获得 Shares                            │
│    │                                             │
│    ├─ 分配新 Vault 存款额                       │
│    │   VaultKeeper.AllocateToVault()            │

#### 为什么一键创建所有组件?

**问题**: 市场创建应该如何设计?

**备选方案**:

1. **方案 A: 分步创建** (用户手动创建每个组件)
   - ✅ 优势: 灵活性高
   - ❌ 劣势: 用户体验差,容易出错

2. **方案 B: 一键创建** ✅ 最终选择
   - ✅ 优势: 用户体验好,降低门槛
   - ❌ 劣势: 灵活性低,默认参数可能不适合所有场景

**决策理由**:

**降低上市门槛**:
- 无权限上市的目标是让任何人都能创建市场
- 分步创建需要深入理解各模块,门槛高
- 一键创建简化流程

**减少错误**:
- 手动创建容易配置错误 (如精度不匹配)
- 自动创建确保配置一致性

**默认参数合理**:
- 长尾市场使用保守参数 (低杠杆、高保证金)
- 可通过治理调整特殊市场

**设计权衡**:
- ✅ 优势: 用户体验优先
- ❌ 劣势: 灵活性牺牲
- 决策理由: 无权限上市的核心是降低门槛

#### 默认参数设计理由

**价格市场参数**:
```
MinPriceChangePpm = 800 ppm (0.08%)

理由:
- 长尾市场价格波动大
- 较高的最小价格变化过滤噪音
- 主流市场通常 < 50 ppm
```

**永续合约参数**:
```
LiquidityTier = 7 (IML 5x)

理由:
- 初始保证金率 20% (5x 杠杆)
- 保守杠杆,降低清算风险
- 长尾市场流动性差,高杠杆危险
```

**Vault 存款参数**:
```
NewVaultDepositAmount = 10,000 USDC
NumBlocksToLockShares = 2,592,000 (约 30 天)

理由:
- 10,000 USDC 提供初始做市流动性
- 30 天锁定期防止闪电贷攻击
- 足够时间观察市场表现
```

            升级完成
    (Isolated → Cross)
```

#### 为什么需要升级功能?

**问题**: 为什么不直接创建 Cross 模式市场?

**原因分析**:

**长尾市场风险**:
- 新上市市场流动性差
- 价格波动大,风险高
- Isolated 模式隔离风险

**成熟市场转换**:
- 市场成熟后,流动性增加
- 价格稳定性提升
- 可以升级到 Cross 模式,提高资金利用率

**单向升级**:
- Isolated → Cross (允许)
- Cross → Isolated (不允许,避免风险)

**设计权衡**:
- ✅ 优势: 灵活风险管理
- ❌ 劣势: 升级流程复杂
- 决策理由: 风险管理优先

### 4.2 下游被依赖

## 5. 技术决策记录 (ADR)

### 5.1 为什么采用无权限上市?

**问题**: 市场创建应该需要许可吗?

**备选方案**:

1. **方案 A: 许可制** (需要治理批准)
   - ✅ 优势: 质量控制,防止垃圾市场
   - ❌ 劣势: 上市速度慢,中心化

2. **方案 B: 无权限** ✅ 最终选择
   - ✅ 优势: 去中心化,上市速度快
   - ❌ 劣势: 可能产生垃圾市场

**决策理由**:

**去中心化优先**:
- DEX 的核心价值是去中心化
- 许可制引入中心化控制点

**市场自然淘汰**:
- 垃圾市场无流动性,自然消亡
- 有价值的市场会获得流动性

**硬上限保护**:
- 通过硬上限防止滥用
- 平衡去中心化和安全性

### 5.2 为什么默认使用保守参数?

(详见 3.1 节)

**决策理由**: 长尾市场风险高,保守参数保护系统

### 5.3 为什么需要 Vault 自动存款?

**问题**: 新市场如何获得初始流动性?

**备选方案**:

1. **方案 A: 用户自行做市**
   - ✅ 优势: 无需协议投入
   - ❌ 劣势: 冷启动困难,无人做市

2. **方案 B: Vault 自动存款** ✅ 最终选择
   - ✅ 优势: 保证初始流动性
   - ❌ 劣势: 协议资金投入

**决策理由**:

**冷启动问题**:
- 新市场无流动性 → 无交易者
- 无交易者 → 无做市商
- 死循环

**Vault 自动做市**:
- 协议提供初始流动性
- 吸引交易者
- 交易者增加 → 做市商进入

**锁定期保护**:
- 30 天锁定期
- 防止立即撤出流动性
- 给市场发展时间

## 6. 总结

### 6.1 关键设计亮点

1. **一键创建**: 简化市场上市流程
2. **无权限**: 去中心化,任何人可创建市场
3. **默认参数**: 保守配置,保护系统
4. **Vault 自动做市**: 解决冷启动问题
5. **升级机制**: Isolated → Cross 灵活转换

### 6.2 设计权衡

| 设计选择              | 优势                 | 劣势                 | 决策理由             |
|---------------------|---------------------|---------------------|---------------------|
| 无权限上市           | 去中心化,速度快       | 可能产生垃圾市场      | 去中心化优先         |
| 一键创建             | 用户体验好           | 灵活性低             | 降低上市门槛         |
| 保守默认参数         | 系统安全             | 限制杠杆             | 风险管理优先         |
| Vault 自动做市       | 解决冷启动           | 协议资金投入         | 市场发展优先         |

### 6.3 Listing 模块的定位

**协调者,不是存储者**:
- 极少数据存储 (仅配置)
- 协调多个模块完成复杂流程
- 体现模块化设计

**无权限的守门人**:
- 允许任何人创建市场
- 通过硬上限防止滥用
- 通过默认参数保护系统
